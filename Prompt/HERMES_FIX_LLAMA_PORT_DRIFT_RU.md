# HERMES: FIX LLAMA-SERVER PORT DRIFT — ROOT-CAUSE AUDIT AND SAFE IMPLEMENTATION (RU)

## Цель

Устранить повторяющуюся проблему: управляемый Hermes `llama-server` запускается то на `127.0.0.1:18434`, то на случайном порту, из-за чего Hermes теряет endpoint, сессии отваливаются, могут запускаться дублирующие серверы и расходоваться лишние RAM/VRAM.

Нужен не косметический workaround, а доказанное исправление первопричины. Сначала исследовать установленную версию и реальный процесс запуска; затем внести минимальное обратимое исправление и проверить его повторными запусками.

## Контекст, который необходимо учитывать

- Рабочая машина: Ubuntu 26, Hermes CLI установлен в `~/.hermes/hermes-agent`.
- Пользователь ранее видел endpoint `http://127.0.0.1:37961/v1`, а в истории есть старый порт `18434`; текущие значения обязательно перепроверь на машине.
- Конфигурация Hermes: `~/.hermes/config.yaml`.
- Логи сервера: `~/.hermes/logs/llama-server.log`; также проверь актуальные логи Hermes и состояние runtime.
- Текущая модель в недавнем отчёте: `Qwen3.5-9B-Q4_K_M`, контекст 65536. Это только подсказка для обнаружения, не разрешение менять модель или контекст.
- Голосовой ввод/вывод сейчас работает. Не ломать и не переустанавливать его.
- Не путать внешний, самостоятельно запущенный `llama-server` с управляемым Hermes runtime/router.

## Важные известные направления расследования

Проверь официальные материалы Hermes Agent, соответствующие именно установленной версии, и сравни их с локальным исходным кодом:

- Документация Local Models: https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/local-models.md
- Issue #113325: конкурентные вызовы `ensure_local_runtime()` могут породить два router-процесса; второй уходит на ephemeral port: https://github.com/NousResearch/hermes-agent/issues/113325
- Issue #105834: обнаружение llama.cpp на нестандартном порту: https://github.com/NousResearch/hermes-agent/issues/105834

Эти материалы — гипотезы и ориентиры, а не доказательство, что локальная установка имеет именно тот же дефект. Не копируй чужой патч вслепую. Проверь статус issue, версию, commit и применимость к текущему коду.

## Жёсткие ограничения безопасности

1. Начни с read-only диагностики. Не меняй конфигурацию, не останавливай процессы и не перезапускай службы до фиксации текущего состояния.
2. Не переустанавливай Hermes, Python 3, llama.cpp, STT/TTS и не меняй голосовой режим.
3. Не меняй модель, provider, API mode, API key, endpoint, context length, GPU layers или параметры CUDA без отдельного доказанного основания.
4. Не печатай API keys, токены и другие секреты в отчёт; маскируй их. Не добавляй конфиги, логи с секретами или локальные ключи в GitHub.
5. Не убивай процессы по одному лишь номеру порта. Сначала установи владельца PID, родительский процесс и способ запуска.
6. Не запускай второй `llama-server` поверх работающего и не запускай несколько экземпляров Hermes для «проверки».
7. Не делай безвозвратных правок в установленном коде. Перед изменением создай резервную копию с временной меткой и запиши точный путь.
8. Не выполняй массовое обновление Hermes и не обновляй зависимости ради этой задачи.
9. Если состояние неоднозначно или тест может прервать текущий диалог, остановись и выдай план с командами для подтверждения пользователем.
10. Не заявляй об успехе, пока результаты тестов не подтверждают его.

## Этап A — собрать исходное состояние

Зафиксируй кратко:

- версию Hermes, путь установки, git commit/dirty state, если применимо;
- текущий `model.provider`, `base_url`, `local_runtime.enabled`, `local_runtime.port` и related runtime settings (значения секретов скрыть);
- какие процессы Hermes и `llama-server` работают, их PID/PPID, командные строки с маскировкой секретов, время запуска;
- слушающие порты и соответствие порт → PID → процесс;
- содержимое runtime state-файла, например `~/.hermes/runtimes/llamacpp/server.json`, если он существует (секреты маскировать);
- свежие строки логов запуска сервера, особенно сообщения про `18434`, `port busy`, `ephemeral`, fallback, health check и повторный запуск;
- текущий ответ `/v1/models` и короткий успешный запрос, если безопасно выполнить без смены состояния;
- точные версии/commit и реальные пути к файлам, где реализованы `ensure_local_runtime`, supervisor start/stop, выбор порта и запись endpoint.

Не выводи весь конфиг целиком, если в нём могут быть секреты. Используй фильтрованное чтение.

## Этап B — доказать первопричину

Проверь как минимум следующие варианты и укажи доказательства за/против каждого:

1. Конкурентные вызовы `ensure_local_runtime()` и неатомарное создание/присваивание supervisor.
2. Порт занят старым или посторонним процессом, и код намеренно выбирает ephemeral port.
3. Остался второй `hermes serve`, дочерний процесс или другой supervisor, запускающий router повторно.
4. Конфиг, runtime state, сохранённая сессия и фактический endpoint расходятся.
5. Процесс-владелец умирает, получает сигнал или запускается повторно из другого жизненного цикла.
6. Hermes использует собственный managed router на одном порту, а пользовательский `llama-server` — на другом; настройки этих двух режимов смешаны.
7. Версия Hermes уже содержит исправление или настройку, отсутствующую в установленной версии.

Найди все call sites запуска runtime, не только один известный метод. Определи, какие потоки/задачи могут вызывать запуск одновременно, и проверь защиту от гонки.

## Этап C — определить правильную политику портов

Целевое поведение:

- Для основного Hermes-managed router используется один стабильный, явно заданный порт (предпочтительно сохранить уже корректно настроенный порт, не выбирать новый без необходимости).
- Если порт занят, НЕ переключаться молча на случайный порт. Выдать понятную ошибку: ожидаемый порт, PID/процесс-владелец, как безопасно диагностировать конфликт.
- Один экземпляр Hermes runtime должен создавать не более одного router/supervisor.
- Все потребители используют согласованный endpoint и корректный API key.
- Временные порты разрешены только тем внутренним процессам, которым они действительно нужны; не запрещай их глобально без проверки архитектуры.
- Явно различай режимы: Hermes-managed runtime и внешний пользовательский `llama-server`. Не заставляй один режим использовать настройки другого.
- Не меняй порт по умолчанию везде автоматически. Выбери порт по фактической текущей конфигурации и документации.
- Если штатная настройка уже решает проблему, используй её вместо патча исходников.

## Этап D — реализация минимального исправления

После диагностики выбери наименее рискованный вариант:

**Предпочтительный порядок:**
1. Использовать существующий документированный параметр/конфиг, если он действительно предотвращает дрейф endpoint.
2. Исправить причину повторного запуска/гонки так, чтобы несколько параллельных вызовов возвращали один и тот же supervisor.
3. Сделать политику конфликта порта явной: стабильный порт + fail-fast при занятом порте вместо молчаливого ephemeral fallback для основного router.
4. Обеспечить согласованную запись/чтение фактического endpoint и корректное восстановление после остановки.
5. Добавить регрессионные тесты.

Не добавляй новый переключатель конфигурации, если достаточно исправить идемпотентность. Если переключатель всё же необходим, задай обратносуместимое поведение и документируй его.

Перед патчем:
- создай timestamped backup;
- сохрани diff;
- запиши команду отката;
- не изменяй файлы за пределами минимально нужных.

## Этап E — тесты, обязательные для объявления успеха

Добавь или выполни подходящие тесты на фактическом установленном коде:

1. Два/несколько параллельных вызовов ensure/start дают один supervisor и один router.
2. При свободном целевом порте сервер поднимается на нём и endpoint совпадает с конфигом/runtime state.
3. При занятом порте сервер не выбирает случайный порт; сообщает о конфликте и владельце порта, если возможно.
4. После штатной остановки и повторного запуска endpoint остаётся тем же.
5. Несколько последовательных запусков/остановок не оставляют старых router-процессов.
6. `/v1/models` и короткий inference-запрос проходят через тот же endpoint; авторизация не теряется.
7. Существующая сессия не продолжает использовать исчезнувший endpoint.
8. Конфигурация внешнего пользовательского `llama-server` по-прежнему работает, если такой режим поддерживается.
9. Запросы к голосовому вводу/выводу и настройки STT/TTS не изменены.
10. Проверь процессное дерево и RAM/VRAM до и после, чтобы исключить дублирование серверов.

Не делай рискованный тест занятости порта на активном рабочем порте. Для unit-тестов используй временный тестовый порт/мок. Live restart проводи только после сохранения состояния и только если можно безопасно восстановить работу.

## Этап F — критерии приёмки

Считать исправленным только при выполнении всех критериев:

- основной endpoint не меняется при обычном повторном запуске;
- нет предупреждения о fallback на ephemeral port в нормальном сценарии;
- конкурентные вызовы не создают два router-процесса;
- конфликт порта виден как ясная ошибка, а не скрытая смена адреса;
- Hermes, runtime state и фактический listener согласованы;
- короткий запрос и несколько последовательных запросов проходят;
- нет новых ошибок авторизации, незапланированного cloud fallback или лишних процессов;
- голосовой режим и параметры модели/контекста сохранены.

Если не получилось проверить какой-либо пункт, укажи его как NOT VERIFIED — не выдавай общий статус STABLE.

## Этап G — отчёт и GitHub

В конце выдай компактный отчёт:

- **Статус:** FIXED / PARTIALLY FIXED / NOT FIXED.
- **Root cause:** конкретный файл, функция, ветка кода и подтверждающие логи/тест.
- **Изменённые файлы:** пути и краткая причина каждого изменения.
- **До/после:** фактический endpoint, количество router-процессов, результаты тестов.
- **Откат:** точная команда/шаги.
- **Непроверенные риски:** список, если есть.
- **Следующий один шаг:** конкретное действие.

Если доступ к GitHub работает:
- сначала проверь, что репозиторий и ветка правильные;
- создай отдельную feature-ветку, не коммить исправление в чужой upstream и не сливай автоматически;
- добавь тесты и документацию, не добавляй локальные конфиги/секреты;
- сделай маленький, объяснимый commit и открой Draft PR только если есть реальное изменение кода и проверяемые тесты;
- не называй Markdown-задание исполняемым скриптом и не заявляй, что PR создан, если создан только prompt-файл.

Если GitHub недоступен, не трать весь контекст на повторные попытки. Сохрани отчёт и патч локально, зафиксируй точную причину отказа и продолжай локальную проверку. Не проси пользователя вручную копировать весь большой текст, если файл уже находится в репозитории.

## Команда к исполнению

Работай поэтапно, не пропускай диагностику. Не останавливайся после обнаружения сообщения `port busy`: докажи, кто занимает порт и почему появляется второй запуск. Не делай косметического изменения только на стороне `base_url`, если реальный сервер всё ещё переезжает. В первую очередь обеспечь единственный supervisor и стабильный endpoint с fail-fast при конфликте. Сохрани рабочую конфигурацию, голосовой режим и возможность отката.
