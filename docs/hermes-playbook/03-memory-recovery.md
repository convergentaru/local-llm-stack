# Hermes: восстановление постоянной памяти и сохранение решений

## Исходный сбой

По отчёту от 2026-10-26 память Hermes превышала указанный лимит: 2303 символа при лимите 2200. Добавление записи не прошло; операции patch/remove не нашли целевые записи, а последующая попытка редактирования завершилась ошибкой. Поэтому считать память обновлённой нельзя.

В том же отчёте указывались:
- локальный документ: docs/HERMES_CONTEXT_WINDOW_FIX_RU.md;
- локальный коммит: 6714112;
- push не выполнен из-за отсутствия GitHub-аутентификации;
- резервная копия: каталог backup_20261020_170520 в профиле Hermes.

Эти пути и статусы относятся к предыдущему отчёту. При повторном запуске нужно проверить их фактическое существование.

## Промпт: восстановить память, потом завершить документацию

~~~
Задача: восстановить работоспособность постоянной памяти Hermes и завершить сохранение проверенного исправления контекстного окна. Работай строго по этапам.

ЭТАП 1. Постоянная память

1. Определи реально используемый механизм памяти в установленной версии Hermes и изучи его поддерживаемые операции чтения/добавления/изменения/удаления.
2. Прочитай полное текущее содержимое, установи фактический лимит и размер. Не угадывай формулировки записей для patch/remove.
3. Сделай резервную копию до изменений.
4. Сохрани уникальные важные сведения: рабочую конфигурацию, голосовое управление, пользовательские предпочтения, проекты и ссылки на документацию. Объедини дубликаты и сократи повторы; не удаляй полезные сведения вслепую.
5. Измени память через поддерживаемый интерфейс. Не считай ручное редактирование файла успешным обновлением памяти, пока не проверена работа механизма.
6. Проверь фактический размер после изменений и выполни отдельную проверку чтения. Если возможно, создай короткую временную запись, прочитай её обратно и удали только эту тестовую запись штатным способом.
7. Если безопасно восстановить память не получилось, остановись. Не очищай всю память и не переходи к этапу 2.

Критерии этапа 1: резервная копия существует, важные записи сохранены, размер в лимите, механизм записи и чтения проверен.

ЭТАП 2. Документация и Git

1. Найди точный исходный промпт исправления контекстного окна в доступной истории и файлах. Не представляй реконструкцию как оригинал.
2. Проверь существующий документ docs/HERMES_CONTEXT_WINDOW_FIX_RU.md. Отдели подтверждённые факты от предположений.
3. Определи фактический корень Git-репозитория, текущую ветку, рабочее дерево, remote и статус коммита 6714112. Не предполагай, что домашний каталог является корнем репозитория.
4. Не удаляй .git/index.lock без проверки активных Git-процессов и подтверждения, что блокировка устарела.
5. Исправь документ минимально, проверь diff и создай отдельный осмысленный коммит при необходимости.
6. Если аутентификация GitHub недоступна, не обходи её и не помещай токены в файлы. Оставь локальный коммит и укажи точную причину, по которой push не выполнен.
7. Через проверенный механизм памяти добавь короткую запись о текущем решении и ссылку на документ. После записи снова проверь чтение и размер памяти.

Краткая запись может сообщать: «Диагностика контекстного окна Hermes описана в docs/hermes-playbook/01-context-window.md. При повторении сверить конфигурацию Hermes, фактическую команду runtime и /props; не сбрасывать текущий рабочий контекст без диагностики». Адаптируй её к фактическим результатам.

Итоговый отчёт должен отдельно указывать результаты этапа 1 и этапа 2, размер памяти, резервную копию, путь документа, статус коммита/push и проведённые тесты. Не утверждай, что чтение или запись работают, если это не проверено.
~~~

## Правило дизайна памяти

- Краткая постоянная память Hermes содержит приоритетные факты и ссылки на документацию.
- Подробные процедуры хранятся в Git.
- GBrain может служить поисковым и долговременным хранилищем, но только после проверки реальной интеграции.
- Не считать любой Markdown-файл автоматически загружаемой памятью Hermes.
- Не удалять важные записи ради освобождения места до резервного копирования и анализа дубликатов.
