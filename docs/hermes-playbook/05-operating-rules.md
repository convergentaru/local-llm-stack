# Рабочие правила использования Hermes Playbook

## Правильная последовательность

1. Если Hermes недоступен, сначала используй 02-api-connection-errors.md.
2. Если соединение работает, но размер/допуск контекста ведёт себя странно, используй 01-context-window.md.
3. После стабилизации системы — 03-memory-recovery.md.
4. Только после проверки памяти и сохранения результатов переходи к 04-hermes-upgrade-gbrain-legal-repair.md.

Не передавай все большие промпты в одну сессию подряд. Это провоцирует переключение задач, раздувание контекста и смешивание результатов.

## Статусы записей

- VERIFIED — проверено воспроизводимым тестом.
- PROVISIONAL — правдоподобно, но проверка неполная.
- FAILED — проверенный подход не работает в описанных условиях.
- UNKNOWN — недостаточно данных даже для уверенной гипотезы.

Дата создания документа сама по себе не делает утверждение VERIFIED.

## Текущее рабочее состояние

По сообщению пользователя от 2026-10-26:
- контекст отображался примерно как 98K после предыдущих настроек;
- Hermes продолжал выдавать APIConnectionError на custom provider в ходе длинной задачи;
- точная причина ошибок соединения не была установлена.

Поэтому:
- не сбрасывать контекст до исторического значения 65536 без диагностики;
- не считать размер 98K доказательством фактического n_ctx inference-сервера;
- сначала проверять соединение и процесс сервера, потом заниматься памятью;
- не считать постоянную память восстановленной до успешного теста записи и чтения;
- не считать документ опубликованным, пока GitHub URL открывается и содержит ожидаемое содержимое.

## Публичный GitHub

Перед каждым коммитом проверяй diff и исключай:
- ключи, токены, пароли и секретные переменные;
- реальные частные юридические материалы;
- персональные данные;
- частные журналы и точные идентификаторы, если они не нужны для воспроизводимости;
- резервные копии конфигураций с секретами.

Публичная документация должна использовать общие пути и примеры, а не раскрывать лишние локальные данные.

## Минимальная постоянная память

Краткая память должна содержать только:
- текущую рабочую архитектуру и критические пользовательские предпочтения;
- ссылки на важные runbook-документы;
- предостережения по известным повторяющимся ошибкам;
- указание, что требуется проверить перед опасными изменениями.

Подробные команды и истории экспериментов хранятся в документации и базе знаний. Не переписывай память целиком, чтобы добавить одну запись; сперва прочитай её, сделай backup и отредактируй только необходимое.
