# Unsloth Studio + Ministral-3-8B + Hermes: эксперимент

**Дата фиксации:** 2026-10-10  
**Статус:** Ministral-3-8B успешно загрузилась в Unsloth Studio. Следующий шаг — проверить фактический процесс `llama-server`, затем подключить Hermes напрямую, без llama-swap и LiteLLM.

## Цель эксперимента

Проверить простую цепочку из трёх компонентов:

1. Собственная сборка llama.cpp.
2. Unsloth Studio для запуска модели.
3. Hermes для дальнейшей работы с моделью.

В этом эксперименте используем **только Ministral-3-8B**. Не запускать Qwen и экспериментальную модель 35B в рамках этой проверки. Старую цепочку Hermes → LiteLLM → llama-swap → llama.cpp временно обходим.

## Изоляция старой цепочки LiteLLM / llama-swap

Для чистого эксперимента службы были остановлены и отключены от автозапуска:

- `llama-swap.service`
- `litellm.service`

Команды, уже выполненные ранее:

```bash
systemctl --user stop llama-swap.service litellm.service
systemctl --user disable llama-swap.service litellm.service
systemctl --user mask --runtime llama-swap.service litellm.service
```

Runtime-маска действовала до перезагрузки; после перезагрузки проверка показала обе службы `inactive`, а порты 8080 и 4000 не слушали. Постоянное отключение автозапуска было проверено отдельно. **Файлы служб не удалялись** — старую архитектуру можно будет восстановить позже.

Последняя проверка после перезагрузки:

```text
systemctl --user is-active llama-swap.service litellm.service
inactive
inactive

ss -ltnp | grep -E ':(8080|4000)\\b' || true
# Совпадений не было; порты 8080 и 4000 не слушали.
```

## Unsloth Studio: процессы и адрес

На момент предыдущей проверки были видны процессы:

- `/usr/bin/unsloth-studio --hidden`
- `/home/oleg/.unsloth/studio/unsloth_studio/bin/python ... unsloth studio --api-only -H 127.0.0.1 -p 8888`

Порт Studio API был настроен на `127.0.0.1:8888`. Это не следует путать с API самого запущенного llama.cpp-сервера: его фактический порт нужно определить после запуска модели.

## Следующие шаги

1. **Не запускать** llama-swap, LiteLLM, Qwen или 35B.
2. Убедиться, что модель продолжает работать в Studio.
3. Одной безопасной командой проверить процессы и выяснить, какой именно `llama-server` запущен:
   ```bash
   pgrep -af 'llama-server|ministral|unsloth'
   ```
4. Если процесс `llama-server` обнаружен, проверить путь к исполняемому файлу через `/proc/<PID>/exe` и его аргументы. Цель — подтвердить, что используется `/home/oleg/llama.cpp/build-cublas/bin/llama-server`, а не встроенная/другая сборка.
5. Определить реальный локальный API endpoint и только после этого настроить Hermes на **Ministral-3-8B** напрямую.
6. Проверить Hermes отдельным коротким запросом. Не менять остальные компоненты стека до успешного теста.

- Целевой контекст Hermes на этом этапе: **64K**.
- KV cache: **q8_0**.
- Для этого эксперимента модель — **Ministral-3-8B**, не Qwen и не 35B.
- Не удалять старые конфиги и службы: они лишь остановлены/отключены.
- Все дальнейшие терминальные действия выполнять по одному шагу, предпочтительно read-only, пока не потребуется явное изменение конфигурации.
