# llmfit — обзор и методика применения

**Дата:** 2026-11-03  
**Установленная версия:** `llmfit 1.1.18`  
**Назначение:** предварительный подбор локальных LLM и контролируемое измерение производительности.

Официальный проект: https://github.com/AlexsJones/llmfit

> Этот документ описывает применение llmfit в Local LLM Stack. Он не заменяет существующий end-to-end benchmark проекта и не разрешает менять рабочую конфигурацию Unsloth без отдельного плана.

## 1. Что такое llmfit

llmfit — инструмент инвентаризации оборудования и предварительного подбора моделей. Он определяет CPU, RAM, GPU и VRAM, затем оценивает модели из своего каталога по нескольким критериям:

- **Fit** — расчётная пригодность по памяти и режиму запуска;
- **Speed / tok/s** — расчётная или измеренная скорость;
- **Quality / Score** — составная оценка качества/пригодности модели для выбранного сценария;
- **Context** — поддерживаемая и используемая при расчёте длина контекста;
- **Quantization / Runtime** — вариант квантования и предполагаемый backend.

llmfit полезен для короткого списка кандидатов. Его расчётный рейтинг не доказывает, что конкретная модель будет качественно писать код, правильно вызывать инструменты Hermes или работать без OOM.

**Важно различать три вида сведений:**

1. **Каталожная оценка** — расчёт llmfit по характеристикам модели и оборудования.
2. **Community benchmark** — замеры других людей; полезны прежде всего для совпадающего оборудования.
3. **Local benchmark** — реальный тест на нашем компьютере и с нашим runtime. Это наиболее ценный результат для нашего решения.

## 2. Как пользоваться интерактивным TUI

Запуск уже установленной версии:

```bash
"$HOME/.local/bin/llmfit" --no-dashboard
```

Основные клавиши (английская раскладка):

| Клавиша | Действие |
|---|---|
| `h` | Показать справку и все горячие клавиши |
| `↑` / `↓`, `j` / `k` | Перемещение по моделям |
| `U` (Shift+U) | Фильтр сценария Use Case; выбрать Coding, Reasoning, Chat и т. д. |
| `C` (Shift+C) | Фильтр возможностей, например Tool Use |
| `f` | Циклический фильтр пригодности: All / Runnable / Perfect / Good / Marginal |
| `s` | Сортировка по Score, Params, Mem%, Ctx, Date или Use Case |
| `/` | Поиск по имени, семейству, параметрам или сценариям |
| `Enter` | Подробности выбранной модели |
| `m`, затем выбрать другую модель и `c` | Сравнить две помеченные/выбранные модели |
| `p` | Plan — оценка требований к оборудованию для выбранной модели |
| `b` | Community leaderboard; для установленной модели с доступным provider может предложить реальный benchmark |
| `I` (Shift+i) | Отдельное представление Inference Bench; может запускать локальные тесты |
| `q` | Выход |

Для фильтра Coding: переключить клавиатуру на English → нажать заглавную `U` → стрелками выбрать `Coding` → `Enter`. Если меню отличается, нажать `h` и пользоваться подсказками конкретной установленной версии.

**Не путать клавиши:** `U` — сценарий Use Case; `C` — возможности; `b` — community/benchmark; `I` — отдельный Inference Bench.

## 3. Как читать таблицу и выбирать модель

Не выбирать победителя только по максимальному Score.

| Поле | Как трактовать |
|---|---|
| Score | Составной рейтинг llmfit. Он зависит от выбранного use case и модели расчёта; это не независимый экзамен качества. |
| Fit | Расчётное размещение на целевом оборудовании. Perfect/Good — хороший фильтр кандидатов, но не гарантия свободной памяти в данный момент. |
| tok/s | Если значение помечено как estimate — прогноз, а не измерение. Ищем measured/local result. |
| Mem% / Memory | Оценка потребности модели в памяти. Нужно проверить, учитывает ли значение текущую занятую VRAM. |
| Params | Число параметров. 25B не автоматически лучше 9B: модель может быть качественнее, но медленнее и требовательнее к памяти. |
| Context | Максимальный контекст из карточки модели не равен контексту, реально заданному серверу. |
| Quant | Q4/Q5/Q8 и другие форматы влияют на размер, качество и скорость. Для нашей GGUF/llama.cpp линии особенно важен GGUF-вариант. |
| Runtime | Для сравнения с текущим Unsloth/llama.cpp в первую очередь проверять совместимость с llama.cpp, а не принимать AWQ/vLLM как взаимозаменяемый вариант. |
| Capabilities | Метки вроде Tool Use — каталожная классификация, не гарантия корректного вызова инструментов в Hermes. |

### Рекомендуемая последовательность отбора

1. Выбрать нужный сценарий: сначала **Coding**, затем отдельно **Reasoning** и **Tool Use**.
2. Поставить фильтр `Runnable`; отдельно изучить `Perfect` и `Good`.
3. Ограничить кандидатов подходящими форматами и runtime. Для нашей основной линии — GGUF + llama.cpp.
4. Открыть детали и посмотреть основание оценки, quantization, память и context.
5. Сравнить 2–4 кандидата через compare. Не загружать их только потому, что они стоят выше в списке.
6. Проверить качество на одинаковых реальных задачах программирования и агентных вызовах.

### CLI для сценария Coding

Команда из официальной CLI-документации:

```bash
"$HOME/.local/bin/llmfit" recommend --json --use-case coding --limit 10
```

Оценка с контекстным ограничением 160K:

```bash
"$HOME/.local/bin/llmfit" --max-context 160000 recommend --json --use-case coding --limit 10
```

`--max-context` ограничивает контекст, используемый для оценки памяти; он **не меняет** контекст уже работающего llama-server и не загружает модель.

Подробный разбор одной записи каталога:

```bash
"$HOME/.local/bin/llmfit" info "точное имя модели из каталога"
```

## 4. Что уже проверено на нашей машине

### Оборудование

Снимки диагностики этой сессии:

| Параметр | Зафиксировано |
|---|---:|
| GPU | NVIDIA GeForce RTX 3060 |
| VRAM всего | 12 GB |
| PCIe | Gen 2 x16 |
| CPU | Intel Core i3-3220, 4 логических CPU в отчёте llmfit |
| RAM всего | около 11.12 GB |
| Доступная RAM по llmfit | около 4.8–4.9 GB |
| Доступная RAM по `free -h` | около 5.1 GiB |
| Swap | 4 GiB; на момент снимка полностью занят |
| GPU memory при загруженной модели | 10,703 MiB занято; 1,209 MiB свободно |

Показатели RAM и GPU сняты в конкретный момент и могут меняться.

### Действующая модель

Через авторизованный запрос к локальному llama-server подтверждены:

- Model: `Qwen3.5-9B-Q4_K_M`;
- файл: `Qwen3.5-9B-Q4_K_M.gguf`;
- quantization: `Q4_K - Medium`;
- настроенный контекст: `160000`;
- parallel slots: `1`;
- Flash Attention: включён;
- vision/video/audio modalities: выключены в ответе сервера;
- сервер управляется текущим Unsloth workflow.

Это подтверждает параметры сервера, а не фактическую длину каждого запроса и не достигнутую скорость.

### Что показал llmfit

- RTX 3060 и CUDA распознаны.
- При стандартном поиске llmfit показал много моделей Qwen 3.5 9B с высокими оценками.
- Предполагаемые 40–48 tok/s в карточках были помечены как estimated; measured TPS отсутствовал.
- В первоначальном отчёте модели поле `memory_available_gb` показывало 12.0 GB, хотя отдельный снимок работающей системы показывал только около 1.2 GB свободной VRAM. Поэтому модельный расчёт нельзя трактовать как свободную память для второй одновременно загружаемой модели.
- Обычный запрос к защищённому `/props` без авторизации вернул HTTP 401. В командной строке процесса обнаружен `--api-key-file`; секрет не публиковался.
- После задания `LLAMA_SERVER_PORT` llmfit сообщал `server_running: true`. Это подтверждает обнаружение endpoint, но не доказывает, что llmfit может пройти авторизацию и выполнить benchmark.
- PID и порт Unsloth менялись между снимками. Нельзя навсегда записывать текущий PID/порт в конфигурацию.

**Итог текущей проверки:** llmfit установлен и полезен для подбора/предварительных оценок. Совместимость его реального benchmark с нашим защищённым Unsloth llama-server пока не подтверждена.

## 5. Как llmfit измеряет реальную производительность

В документации llmfit указано, что benchmark работает против уже запущенного provider. Для llama-server можно использовать обнаружение на стандартном порту 8080 либо задать `LLAMA_SERVER_HOST` (полный URL) или `LLAMA_SERVER_PORT`; provider можно явно выбрать как `llamacpp`.

Пример общей формы команды, **не команда для запуска сейчас**:

```bash
LLAMA_SERVER_PORT=PORT llmfit bench --provider llamacpp
```

При успешном тесте llmfit выполняет три реальных inference-запуска и измеряет tok/s и TTFT. Результаты сохраняются локально; публикация через `--share` — отдельное добровольное действие и создаёт Pull Request в upstream llmfit.

### Ограничение нашей конфигурации

В официальной документации перечислены `LLAMA_SERVER_HOST` и `LLAMA_SERVER_PORT`, но отдельная настройка API-ключа для llama-server в описании provider не приведена. Наш текущий сервер требует API-ключ через файл. Поэтому нельзя считать, что команда выше пройдёт авторизацию. **Не отключать API-key, не выводить ключ в терминал и не передавать его в командной строке ради benchmark.** Сначала нужно отдельно подтвердить безопасную совместимость аутентификации с установленной версией llmfit.

Не путать benchmark с простым обнаружением: `server_running: true` не означает, что inference-запрос авторизован и успешно выполнен.

## 6. Как измерять модели в нашем проекте

У нас есть два разных вида измерений. Их нельзя сводить в одну таблицу без пояснения.

### A. llmfit local benchmark

Назначение: получить TTFT и реальную скорость inference для поддерживаемого локального provider. Это измерение самого inference endpoint. По документации один benchmark включает три inference-прохода.

Хорошо подходит для измерения после того, как provider доступен и аутентификация подтверждена. Результаты llmfit сохраняются в его локальном хранилище; их можно открыть в community view как `you (local)`. Не добавлять `--share`, пока отдельно не принято решение публиковать показатели в upstream.

### B. Существующий benchmark Local LLM Stack

Файл: [`../benchmark-stack.sh`](../benchmark-stack.sh)

Он тестирует полный путь через LiteLLM и llama-swap, а не только чистый llama-server endpoint. Скрипт записывает HTTP status, полное время запроса, prompt TPS и generation TPS, если runtime вернул timings.

Текущий скрипт делает один основной запрос на каждую модель из фиксированного списка. Поэтому его результаты полезны как end-to-end smoke/performance snapshot, но это не полноценный статистический тест с серией повторов. Он может переключать модели через стек; не запускать его во время критичной рабочей сессии Hermes/Claude Code без отдельного окна тестирования.

### Протокол честного сравнения

Для кандидатов фиксировать одинаковые условия:

- одна и та же машина и версия backend;
- один runtime и сопоставимое GPU-offload;
- точный model ID, файл и quantization;
- одинаковый контекст (отдельно тестировать, например, 8K/32K/64K; 160K — только когда подтверждён запас памяти);
- одинаковые prompt/input tokens и одинаковый лимит output tokens;
- одинаковые temperature и generation settings;
- холодный запуск и тёплая генерация записываются раздельно;
- минимум три сопоставимых повтора; для ручных серий сохранять медиану;
- одновременно загружена только одна тестируемая модель;
- до/после фиксировать VRAM, RAM, swap, температуру GPU и состояние процессов.

Записывать: TTFT, prompt tokens/s, generation tokens/s, total latency, prompt/output tokens, HTTP status, VRAM/RAM/swap, exit/error, качество ответа и результат проверок кода.

**Для Coding отдельная оценка качества обязательна:** одинаковая задача, одинаковый репозиторий/тесты, проверка компиляции или тестов, правильность изменений, отсутствие лишних правок, успешность tool calls. Одна скорость tok/s не определяет лучшую coding-модель.

## 7. Правила безопасности для текущего компьютера

На момент диагностики Qwen уже занимала около 10.7 GB VRAM из 12 GB, а swap был заполнен. Поэтому:

- не запускать `I`, `b` с подтверждением реального benchmark или `llmfit bench` во время текущей рабочей нагрузки;
- не скачивать и не загружать вторую модель;
- не запускать второй `llama-server`;
- не менять Unsloth, контекст, KV cache, API key или firewall;
- не использовать `--share` без отдельного согласования;
- не считать каталог `Perfect` доказательством, что модель можно загрузить поверх текущей Qwen.

Первый этап — пассивный просмотр каталога, фильтры и детали моделей. Реальный тест — отдельный контролируемый этап после проверки памяти, provider/auth и окна обслуживания.
